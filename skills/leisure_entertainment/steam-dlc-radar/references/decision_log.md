### D4 - DLC评价摘要

### D5 - 定时任务执行策略
- **结论**：~~每天一次，通过Marvis MCP工具实现~~ → 每个订阅游戏生成一条独立定时任务 query，AI 原生能力执行，Skill 只负责生成 query 话术
- **决策日期**：2026-04-15，2026-04-20更新
- **状态**：✅ 已定（v1.1 重构）

### D6 - 定时任务判新机制
- **结论**：~~通过"昨天"时间窗口判新~~ → 通过本地缓存对比判新。脚本每次获取当前 DLC ID 列表，与缓存的上次列表对比，新增的即为新 DLC。首次查询全量缓存，后续只报新增。缓存文件 `scripts/data/dlc_cache.json`
- **决策日期**：2026-04-20，2026-04-21更新
- **状态**：✅ 已定（v1.2 → v1.4 改为缓存对比）

### D7 - Steam API 调用策略
- **背景**：Steam Store API (`store.steampowered.com`) 国内可达但不稳定；第三方替代方案均不可行（SteamDB 禁止爬取，IsThereAnyDeal 无"游戏→DLC列表"接口）；用个人 API Key 给所有用户共享有限流/封号/泄露风险
- **结论**：预置 Python 脚本 `scripts/check_dlc.py`，内置3次重试+8秒超时+指数退避+本地缓存。禁止 AI 临时生成脚本调 Steam API。查询失败时如实告知用户"Steam 国内访问不稳定，建议开加速器重试"
- **决策日期**：2026-04-21
- **状态**：✅ 已定（v1.4）

### D8 - 订阅信息收集策略
- **背景**：实测发现，如果分两轮收集信息（先问"要订阅吗"→再追问"几点检查"），第二轮用户给出时间后，AI 不会生成定时任务。但如果用户一次性说"订阅，每天10点"，定时任务能正常生成。根因是多轮对话中定时任务创建动作丢失
- **结论**：订阅意愿和检查时间**合并为一个问题一起问**，不拆两轮。用户只要表达订阅意愿（无论是否带时间），AI 必须当场生成定时任务，没指定时间就用默认 10:00，绝不追问时间
- **决策日期**：2026-04-21
- **状态**：✅ 已定（v1.5）

### D9 - 活跃数据来源
- **背景**：Skill 原设计中有"应用宝活跃数据MCP"作为补充优化项，用于自动推荐用户最近在玩的游戏。实测发现当前无此接口，但 Skill 中多处引用导致 AI 每次都尝试探索该接口是否存在，浪费交互
- **结论**：彻底移除所有应用宝活跃数据/MCP 相关逻辑。游戏名完全由用户输入。若未来接口就绪，再作为新版本加回
- **决策日期**：2026-04-21
- **状态**：✅ 已定（v1.6）

### I2 - 定时任务结论输出格式
- **结论**：~~Marvis新上线MCP工具~~ → 定时任务是 AI 原生能力，做在接入层底层，不需要调用特定 MCP 接口。Skill 生成 query，系统到时间自动执行并推送结果
- **状态**：✅ 已明确（2026-04-20）

### I3 - 用户看到结论的交互形式
- **结论**：由系统负责将定时任务执行结果推送给用户，Skill 不需关注推送形态
- **状态**：✅ 已明确（2026-04-20）

### I4 - 看到结论后能否继续对话
- **结论**：由系统侧决定，Skill 不管控
- **状态**：✅ 已明确（2026-04-20）

### I5 - 定时任务能否调用外部API
- **结论**：~~定时任务触发时 = AI 执行一次完整对话，可正常调用 Steam API 等外部接口~~ → 定时任务通过预置脚本 `scripts/check_dlc.py` 调用 Steam API，脚本在用户本机运行，网络取决于用户环境（国内不稳定，需加速器）
- **状态**：✅ 已明确（2026-04-21 更新）

### I6 - 定时任务触发频率限制
- **结论**：由系统能力决定，当前按每天一次设计，每个游戏一条独立任务
- **状态**：✅ 已明确（2026-04-20）
