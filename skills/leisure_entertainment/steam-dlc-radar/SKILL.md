## Overview

DLC雷达是应用宝Marvis AI对话中的Steam游戏DLC发现与订阅服务。通过两个互补方案帮用户及时了解和追踪游戏DLC动态：

- **方案1（被动/对话嵌入）**：用户聊到Steam游戏时，自动检测并带出DLC信息
- **方案2（主动/功能卡片）**：用户点击DLC雷达卡片，多路径查询DLC动态

订阅后，定时任务每天检查所有订阅游戏的DLC变化，有新内容时推送，无变化时静默。

## 方案1：对话中自然嵌入（被动触发）

### 触发条件

同时满足以下三点才触发：
1. 用户在对话中提到了某个Steam游戏
2. 该游戏**有DLC**（没有DLC则完全不触发，不打扰）
3. 用户的意图是**聊游戏本身**（讨论、推荐、评价、询问），而非问攻略/Bug/具体玩法

### 触发规则

| 规则 | 说明 |
|------|------|
| 品牌前缀 | 固定使用「DLC雷达」作为信息来源标识 |
| 重复控制 | 同一对话内，同一游戏只触发一次；跨对话（新session）可重新触发 |
| 拒绝处理 | 用户忽略或拒绝订阅，不影响后续触发——下次符合条件照常触发+照常引导订阅 |
| 无DLC | 完全不触发，不出现任何DLC相关内容 |

### 流程

1. 识别用户提到的游戏名 → 匹配Steam AppID
2. 执行预置脚本查询 DLC 列表（见「Steam API 调用策略」章节）
3. 有DLC → 带品牌前缀展示DLC概览 + 引导订阅
4. 无DLC → 静默，不触发
5. 查询失败 → 告知用户 Steam 国内访问不稳定，建议开加速器后重试

## DLC 信息展示规则

> 以下规则适用于所有展示DLC的场景：方案1被动触发、方案2主动查询。（定时任务只检测新DLC，展示规则简化。）

### 四层信息模型

| 层级 | 内容 | 规则 |
|------|------|------|
| **L1 基础信息** | DLC名称、价格、上线时间 | 每个DLC必须展示 |
| **L2 评价汇总** | 好评/差评分开总结 | 按评论数量分级（见下方） |
| **L3 性价比评级** | ★评分 + 一句话结论 | 综合价格、内容量、口碑给出 |
| **L4 入手建议** | 历史低价 + 下次大促预测 | 可选，有数据就给，没有不编造 |

### 评价分级策略

| 评论数 | 展示方式 |
|--------|---------|
| ≥1000条 | 完整展示：好评率 + 多条👍好评 + 多条👎差评（每条一行，emoji直接开头，同类连续不加空行，不同类型之间空行分隔） |
| 100-999条 | ⭐ 好评率（评论数）+ 📣 一句话评价摘要 |
| <100条 | ⭐ 好评率（评论较少） |
| 无评论 | 暂无玩家评价 |

### 性价比评级规则

综合以下因素给出 ★ 评分（1-5星）：
- **内容量**：DLC 提供的游玩时长/内容规模
- **价格**：绝对价格 + 相对本体的价格占比
- **口碑**：好评率和评论数

```
💎 ★★★★☆（4/5）20-40小时内容量对得起¥198定价，核心粉丝必入，对Boss难度敏感建议先看攻略。
```

### 入手建议规则

有以下信息时展示，没有不编造：
- **历史最低价**：来自 Steam 促销记录
- **下次大促预测**：Steam 夏促（6月底）、冬促（12月底）、秋促（11月底）为固定大促节点
- **购买建议**：急玩/等折扣的简明建议

```
💡 历史最低 ¥139（2025冬促，-30%），下次机会：2026夏促（6月底）。急着玩现在买不亏，想省钱等夏促更划算。
```

### 捆绑包/季票提示

游戏有 DLC 捆绑包（Season Pass / 年度版 / 完全版）时，在 DLC 列表末尾提示：

```
💡 该游戏有「年度版」捆绑包 (¥298)，包含全部DLC，比单买省 ¥120
```

> 有捆绑包就提示，没有不提。

### 排版规则

> 以下规则确保在 Marvis 对话窗口中渲染清晰：

1. **禁止使用 `- ` bullet 黑点**：所有信息行直接用 emoji 开头（💰/👍/👎/💎/💡等），不加 `- ` 前缀
2. **同类信息连续排列不加空行**：多条 👍 之间、多条 👎 之间紧贴
3. **不同类型信息之间用空行分隔**：如 👍 区和 👎 区之间、👎 区和 💎 之间、💎 和 💡 之间各空一行
4. **DLC 标题与第一行信息之间空一行**：📦 标题后空一行再接 💰 行
5. **多个 DLC 之间用 `---` 分隔线**

💰 ¥198 | 📅 2024-06-21 上线 | ⭐ 70% 好评（41,253条）

👍 新武器/战灰种类多，build多样性提升

👎 Boss难度曲线陡峭，终Boss争议大

👎 地图后半段赶工感明显

💎 ★★★★☆（4/5）20-40小时内容量对得起¥198定价，核心粉丝必入。

💡 历史最低 ¥139（2025冬促，-30%），下次机会：2026夏促（6月底）。急玩现在入不亏，等促销更划算。

### DLC 分页策略

| DLC 数量 | 展示方式 |
|----------|---------|
| ≤3 个 | 全部展开完整详情 |
| 4-6 个 | 展开前 3 个（按排序规则），剩余折叠，提示"还有 X 个DLC，回复「继续」查看" |

| 优先级 | 规则 |
|--------|------|
| 1 | 上线时间**最近**的排前面 |
| 2 | 同期上线的按**好评率**从高到低 |

## 订阅机制

### 订阅方式

**一步收齐（订阅意愿 + 检查时间一起问）**：

引导订阅时，**必须在同一句话里同时问是否订阅和检查时间**，不要分两轮。这样用户一次回复就能带全信息，AI 当场生成定时任务。

> ⚠️ **禁止分两轮问**：先问"要订阅吗"→再追问"几点检查"会导致多轮对话中定时任务生成失败。必须合并为一个问题。

引导话术模板：
```
要订阅这个游戏的DLC通知吗？有新DLC上线我会提醒你 🎯
默认每天 10:00 检查，你也可以指定时间（比如"订阅，每天早上9点"）
```

用户可能的回复及处理：
| 用户回复 | AI 动作 |
|---------|--------|
| "订阅" / "要" / "好" | 用**默认时间 10:00**，立即生成定时任务 |
| "订阅，每天早上9点" | 用用户指定的时间，立即生成定时任务 |
| "订阅，9点" | 用用户指定的时间，立即生成定时任务 |
| "不用了" / 忽略 | 不订阅，不追问 |

> **核心规则**：用户只要表达了订阅意愿（无论是否带时间），AI 必须**当场生成定时任务**，没指定时间就用默认 10:00。绝不追问时间。

> 注：DLC打折通知不在本Skill范围内，由另一个专门的Steam折扣订阅Skill负责。

### 订阅管理

全在对话中完成，不需要单独管理页面：

| 操作 | 触发方式 |
|------|---------|
| 查看订阅列表 | 卡片进入后选"查看已订阅的游戏" |
| 取消订阅 | 对话中说"取消XX的DLC订阅" |
| 新增订阅 | 正常查询流程后选择订阅 |

### 订阅数据存储

存储位置：Skill本地文件 `data/subscriptions.json`

> 注：此文件仅用于 AI 在对话中管理订阅列表（查看/新增/取消），**不用于定时任务执行**。定时任务是独立的 query，由系统调度执行，不依赖此文件。

数据结构：
```json
{
  "user_subscriptions": {
    "subscribed_games": [
      {
        "game_name": "Elden Ring",
        "game_name_cn": "艾尔登法环",
        "app_id": 1245620,
        "check_time": "09:00",
        "subscribed_at": "2026-04-15"
      }
    ]
  }
}
```

## 订阅定时任务

### 核心机制

用户订阅游戏DLC后，AI **为每个游戏生成一条定时任务**。定时任务的本质是一条固定话术的 query + 用户指定的执行时间，系统到时间自动用这条 query 触发 AI 执行一次，执行结果由系统负责推送给用户。

**Skill 负责两件事：生成定时任务 query + 设定执行时间（来自用户选择）。不负责任务怎么执行、结果怎么推送。**

### 定时任务 query 模板

每个订阅游戏生成一条独立的定时任务，query 话术如下：

```
帮我检查Steam游戏「{游戏中文名}」（AppID: {app_id}）是否有新上线的DLC。
请执行预置脚本 scripts/check_dlc.py 来查询：
  python scripts/check_dlc.py --app_id {app_id} --game_name "{游戏中文名}" --json
脚本会自动处理重试和缓存，将输出 JSON 结果。
根据脚本输出：
- 如果有新DLC（new_dlc 不为空），列出新DLC的名称、价格、上线时间，如已有足够评论附上好评率和玩家评价摘要。
- 如果没有新DLC，回复"暂无新DLC"。
- 如果脚本执行失败（success=false），将 error 信息如实告知用户，提示"Steam 在国内访问不稳定，建议开启加速器后重试"。
```

**变量说明**：
| 变量 | 来源 | 示例 |
|------|------|------|
| `{游戏中文名}` | 订阅时记录 | 艾尔登法环 |
| `{app_id}` | Steam API 匹配 | 1245620 |

**判新机制**：通过本地缓存对比判新。脚本每次执行时获取游戏当前 DLC ID 列表，与本地缓存的上次 DLC ID 列表对比，新增的即为新 DLC。首次查询时全量缓存，后续只报新增。缓存文件：`scripts/data/dlc_cache.json`。

### 生成规则

| 规则 | 说明 |
|------|------|
| 粒度 | **每个游戏一条**独立定时任务 |
| 频率 | 每天一次（建议上午10:00） |
| 订阅时 | 立即生成该游戏的定时任务 |
| 取消订阅时 | 删除对应游戏的定时任务 |

## 游戏匹配策略

### 游戏名 → Steam AppID

**筛选流程**（对用户不透明）：
1. 获取游戏名（用户输入）
2. 利用AI游戏知识初步判断是否为Steam游戏
3. 不确定的通过预置脚本查询 Steam Search API 验证
4. 匹配成功记录AppID，失败静默跳过
5. 只向用户展示确认是Steam游戏的结果

**注意**：
- 游戏名可能是中文、英文或混合，需做模糊匹配
- 同一游戏有多个版本时以Steam版为准

## Steam API 调用策略

### 网络环境

Steam Store API（`store.steampowered.com`）在国内可达但**不稳定**——域名未被墙，但经常丢包、超时、速度慢。**没有替代数据源**：能返回"游戏→DLC列表"关系的全球只有这一个接口，第三方（SteamDB 禁止爬取、IsThereAnyDeal 没有该关系接口）均不可替代。

### 执行方式

**禁止 AI 临时生成脚本调用 Steam API**。所有 Steam API 调用统一通过预置脚本 `scripts/check_dlc.py` 执行：

| 场景 | 执行命令 |
|------|---------|
| 查询单个游戏（定时任务/主动查询） | `python scripts/check_dlc.py --app_id {id} --game_name "{name}" --json` |
| 查询完整 DLC 列表 | 追加 `--full` 参数 |
| 批量检查所有已缓存游戏 | `python scripts/check_dlc.py --check_all --json` |

### 脚本特性

| 特性 | 说明 |
|------|------|
| **3次重试** | 每次请求失败自动重试，最多3次 |
| **8秒超时** | 单次请求超过8秒自动放弃 |
| **指数退避** | 重试间隔 2s → 4s → 8s，避免密集请求 |
| **本地缓存** | DLC 列表缓存到 `scripts/data/dlc_cache.json`，用于对比新增 |
| **请求间隔** | 多个 DLC 逐个查询，间隔 0.5s |
| **JSON 输出** | `--json` 参数输出结构化 JSON，方便 AI 解析 |

## 失败处理策略

### 原则

> **宁可不报，不能误报。** 查询失败时如实告知用户原因和解决方案，不编造数据。

### 失败时回复模板

```
⚠️ DLC 检查暂时失败

Steam 商店在国内访问不太稳定，本次未能成功获取数据。

💡 你可以：
1. 开启加速器后，说"再查一次"重试
2. 稍后再试（不同时段网络状况可能不同）

放心，已订阅的游戏明天会自动再查 🔔
```

### 部分失败处理

脚本可能获取了游戏本体信息（成功），但部分 DLC 详情查询超时。此时：
- 成功获取的 DLC 正常展示
- 失败的 DLC 标注"详情获取失败"
- 缓存仍更新（以成功获取的数据为准）
